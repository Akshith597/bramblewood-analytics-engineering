## In short

- **The problem.** Bramblewood, a fictional {stores}-store retailer, is reviewing its salty-snacks aisle for next year. Its sales, inventory and merchandising data come from separate systems that don't line up, so simple questions like "which products should we cut?" give different answers depending on who joins the files.
- **What I built.** A tested SQL warehouse (dbt + DuckDB) that cleans and joins those files so every dollar of sales reconciles back to the source, and an analysis on top that answers the category director's five questions about products, promotions, prices, forecasting and vendor payments.
- **The result.** A one-page plan worth an estimated **{plan_total} of gross profit a year** (90% range {plan_range}). Most of it comes from dropping promotions that only look profitable because vendors pay for them.

## The problem

POS identifies products by UPC and week-ending date. Inventory uses SKU and fiscal week. Merchandising supplies effective-dated prices, costs and planograms. Joining them naively creates duplicate revenue, misaligned dates, temporal-join fanout and misleading metrics.

The objective is a **reproducible, auditable warehouse that business users can query safely** — with every cleaning decision traceable and every ambiguity left visible rather than silently "fixed".

## Engineering decisions that mattered

| Source issue | Decision | Verified result |
|---|---|---|
| Concatenated POS feeds | Classify every row; remove exact replays only | {replay_rows} replay rows (**{replay_sales}**) excluded; one embedded header retained in audit |
| Inconsistent product/date formats | String UPC normalization and two explicit date formats | {upcs_padded} UPCs padded; {legacy_dates} legacy-format dates parsed |
| Overlapping cost history | Latest-start precedence; original dates kept with an exception flag | {cost_rows} affected sales rows; **{cost_cogs} COGS sensitivity** disclosed |
| Return transactions | Preserve signed units and amounts | {return_rows} return rows retained instead of dropped as "invalid" |
| Inventory without sales | Keep both sides with presence flags | {inventory_only} inventory-only observations remain visible |
| Forecast at chain grain | Aggregate actuals to chain SKU-week before joining | No store-level fanout in forecast measures |
| Many claims per promotion | Aggregate claims and eligible units before joining funding terms | Funding gap computed without double counting; cancelled-event claims ({cancelled_billed}) kept separate |

The most instructive failure: the cost-overlap test initially failed for `SS-1081`, whose old cost ended two weeks *after* the new one began. A direct join would have duplicated sales rows and inflated revenue. The full story is in the [case study](docs/case_study.md#the-most-instructive-failure).

## Run it locally

Python 3.12; no cloud account or credentials required.

```bash
python -m venv .venv
# Windows: .venv\Scripts\Activate.ps1   macOS/Linux: source .venv/bin/activate
python -m pip install -r requirements-dev.txt
python scripts/run_all.py               # ingest → dbt build → reconcile → docs → evidence → charts
python -m analysis.run                  # analyses → analysis/results → memo, plan, scorecard, README
python scripts/verify_repeatability.py
python -m unittest discover -s tests_python -v
python scripts/lint_sql.py
```

Browse lineage and compiled SQL locally with `python scripts/invoke_dbt.py docs serve --port 8080`, and open `target/insights.html` for the dashboard. See the [runbook](docs/runbook.md) for troubleshooting.

The raw extracts in `data/raw/` (about 20 MB) are committed as ordinary Git files on purpose: a plain clone rebuilds everything offline, with no Git LFS setup or download step. The files never change, so they don't grow the history.

## Scope and limitations

This is a local batch warehouse, not a deployed production platform. It uses deliberate full rebuilds because the extracts lack reliable change timestamps. Item and store dimensions reflect the supplied current master; cost, price and planogram periods are effective-dated. Cost precedence is a documented assumption. A zero-stock snapshot does not establish lost sales, and approved promotion eligibility does not establish realized lift or funding entitlement.

Next production steps: source-owner resolution of exceptions, validated incremental restatement, isolated build/publish schemas and freshness monitoring. See the [design decisions](docs/architecture.md) for the tradeoffs.
