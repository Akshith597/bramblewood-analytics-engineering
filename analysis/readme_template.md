## The problem

A fictional {stores}-store retailer needs consistent answers about sales, inventory, promotions and vendor funding. Disconnected extracts use different keys, dates and grains; naive joins duplicate revenue and distort decisions.

## Engineering decisions that mattered

| Source issue | Decision | Verified result |
|---|---|---|
| Concatenated POS feeds | Classify every row; remove exact replays only | {replay_rows} replay rows (**{replay_sales}**) excluded; one embedded header retained in audit |
| Inconsistent product/date formats | String UPC normalization and two explicit date formats | {upcs_padded} UPCs padded; {legacy_dates} legacy-format dates parsed |
| Overlapping cost history | Latest-start precedence; original dates kept with an exception flag | {cost_rows} affected sales rows; **{cost_cogs} COGS sensitivity** disclosed |
| Return transactions | Preserve signed units and amounts | {return_rows} return rows retained instead of dropped as "invalid" |
| Inventory without sales | Keep both sides with presence flags | {inventory_only} inventory-only observations remain visible |
| Forecast at chain grain | Aggregate actuals to chain SKU-week before joining | No store-level fanout in forecast measures |
| Many claims per promotion | Aggregate claims and eligible units before joining funding terms | Funding gap computed without double counting; cancelled-event claims ({cancelled_billed}) kept separate |

The most instructive failure: the cost-overlap test initially failed for `SS-1081`, whose old cost ended two weeks *after* the new one began. A direct join would have duplicated sales rows and inflated revenue. The full story is in the [case study](docs/case_study.md#the-most-instructive-failure).

## Production patterns

- **Incremental fact table.** `fct_sales` restates whole fiscal weeks inside a trailing lookback window (`delete+insert` on `week_key`), so rows dropped from a corrected extract disappear too. Backdated cost or master-data corrections go through `--full-refresh`; the repeatability check proves the incremental path matches a full build. [Design decision](docs/architecture.md#adr-02--deterministic-full-rebuild)
- **Type 2 history.** dbt snapshots track item and store master changes on attribute columns only, with tests for one current version per key and non-overlapping validity windows. [Data contracts](docs/data_contracts.md)
- **Source freshness.** `dbt source freshness` warns, then fails, when raw tables stop being reloaded. A separate [publication workflow](docs/runbook.md#validated-batch-publication) checks source hashes and extraction age before atomically switching a release pointer.
- **Portable SQL.** DuckDB-only expressions go through dispatched macros, and an optional Snowflake target compiles the models. It has not run against a live account. [What is ported](docs/architecture.md#running-on-snowflake)

What it did measure cleanly: units fell {d_units} but net sales changed only {d_sales}, because shoppers switched to the items that stayed (retained items recovered {d_transfer} of the lost sales, {d_transfer_ci}). | Don't roll out the test planogram; cut the {a_cuts} SKUs that earn the least gross profit per facing ({a_value}) |
| Promotions | **Roughly break-even, and only because of vendor money.** FY2025 events net {q2_net} ({q2_ci}) after funding and {q2_before} before it; {q2_pos_before} of events made money on their own. | Drop promotions without a display; keep display events where execution is verified and the fee collected |
| Spring 2025 price increases | **Not identified** by either event design. | Vendor funding | Scan-back under-billed on approved events by {v_low} to {v_high}; a range, because display execution is not observable. | Bill the scan-back shortfall now; verify displays before billing them |

## Run it locally

Python 3.12; no cloud account or credentials required.

```bash
python -m venv .venv
# Windows: .venv\Scripts\Activate.ps1   macOS/Linux: source .venv/bin/activate
python -m pip install -r requirements-dev.txt
python scripts/run_all.py               # ingest → freshness → dbt build → reconcile → docs → evidence → charts
python -m analysis.run                  # analyses → analysis/results → memo, plan, scorecard, README
python scripts/verify_repeatability.py
python -m unittest discover -s tests_python -v
python scripts/lint_sql.py
```

Browse lineage and compiled SQL locally with `python scripts/invoke_dbt.py docs serve --port 8080`, and open `target/insights.html` for the dashboard. See the [runbook](docs/runbook.md) for troubleshooting.

## Scope and limitations

This is a local batch warehouse, not a deployed production platform. Item and store dimensions reflect the supplied current master; snapshots record changes only from a warehouse's first build, and cost, price and planogram periods are effective-dated. Cost precedence is a documented assumption. A zero-stock snapshot does not establish lost sales, and approved promotion eligibility does not establish realized lift or funding entitlement. Source-owner exception resolution, alert delivery and managed scheduling remain future work. See the [design decisions](docs/architecture.md) for the tradeoffs.

The raw extracts in `data/raw/` (about 20 MB) are committed as ordinary Git files on purpose: a plain clone rebuilds everything offline, with no Git LFS setup or download step. The files never change, so they don't grow the history.

## How I built this

This project was built with AI assistance. The Git history includes Claude-authored implementation commits and links to Claude Code sessions. That history is retained so the development process is visible.

Verification is part of the repository: dbt tests and contracts, independent raw-file sales reconciliation, repeatability checks, and Python and R estimator cross-checks run in CI. These checks provide evidence about correctness; they do not establish sole human authorship or validate every business assumption. Design choices and limitations are recorded in the [architecture decisions](docs/architecture.md) and [analysis plan](analysis/PLAN.md).

For a warehouse walkthrough, start with the SQL in [staging](models/staging/), [intermediate](models/intermediate/) and [marts](models/marts/). Python handles ingestion, statistical analysis, evidence exports and document generation; its size reflects that broader analysis and tooling layer.
